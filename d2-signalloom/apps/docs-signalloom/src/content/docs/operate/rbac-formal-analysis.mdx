KubeSec Automated Formal Methods (KubeSec-AFM) verifies Kubernetes Role-Based Access Control (RBAC) configurations using mathematical logic.

It converts cluster policies into first-order logic formulas and uses the Z3 Satisfiability Modulo Theories (SMT) solver to find security flaws.

## The Verification Problem

Traditional Kubernetes security scanners use static heuristic rules. Static heuristics fail to detect multi-step privilege escalation paths across different subjects.

KubeSec-AFM uses Bounded Model Checking (BMC). It examines all possible state transitions up to a bounded depth $k$ to prove whether an untrusted agent can reach administrative privileges.

## Capabilities and Attack Classes

KubeSec-AFM detects four primary classes of access control vulnerabilities:

### 1. Direct Self-Escalation Paths

Direct escalation occurs when an unprivileged subject possesses permissions that modify authorization policies. Examples include:
- `bind` or `escalate` verbs on `ClusterRoles`
- `create` or `patch` permissions on `RoleBindings`
- `create` permissions on `pods/exec` or workload controllers

### 2. Impersonation Chains

Kubernetes permits subjects to impersonate other users, groups, or service accounts. KubeSec-AFM computes transitive closures over impersonation chains:

### 3. Cross-Subject Collusion Cliques

Collusion occurs when two or more agents combine separate permissions to achieve privilege escalation. Individual agents appear safe in isolation, but their combined access breaches separation-of-duty boundaries.

### 4. Min-Cut Remediation

When Z3 identifies an attack path, the engine calculates the minimum-cut graph edge removal. This computes the smallest policy modification that blocks the attack path with minimal operational impact.

## Inspecting RBAC in the Dashboard

Signal Loom provides two dedicated user interfaces to explore formal verification results.

### The RBAC Analysis View (`/rbac-analysis`)

Navigate to **RBAC Analysis** in the main sidebar. This page displays:
- Overall cluster security posture score
- Number of evaluated subjects, roles, and bindings
- Active counterexample attack paths ranked by severity
- Recommended policy diffs generated by the Min-Cut engine

### The RBAC Graph Explorer (`/rbac-explorer`)

Navigate to **RBAC Explorer** to examine the interactive access graph.
- Filter nodes by namespace, subject type, or target resource.
- Highlight shortest escalation paths from any selected node to `cluster-admin`.
- Inspect effective permissions computed across all bindings.

## Running an On-Demand Verification

You can execute a formal verification check using the command-line interface.

### 1. Verify AFM Service Status

Before running an analysis, check that the AFM backend service is running:

```bash
kubectl get pods -n k8s-afm -l app=afm-platform
```

The output must show `Running` status.

### 2. Trigger Formal Analysis

Run the verification script from the repository root:

```bash
make demo-k8s-afm-status
```

To run a deep bounded search with step depth $k=6$:

```bash
./scripts/k8s-afm.sh analyze --depth 6 --namespace default
```

### 3. Review the Solver Output

If the cluster configuration is safe, the solver returns:

```text
Result: UNSAT
Verification status: PROVEN_SECURE
No escalation paths exist within bound k=6.
```

If a vulnerability exists, the solver returns a counterexample attack trace:

```json
{
  "result": "SAT",
  "vulnerability": "SelfEscalationViaRoleBinding",
  "subject": "system:serviceaccount:default:dev-agent",
  "target": "cluster-admin",
  "steps": [
    { "step": 1, "action": "create", "resource": "rolebindings", "role": "admin" },
    { "step": 2, "action": "bind", "subject": "system:serviceaccount:default:dev-agent" }
  ],
  "min_cut_remediation": [
    { "type": "REVOKE_VERB", "role": "dev-role", "verb": "create", "resource": "rolebindings" }
  ]
}
```

Apply the recommended `min_cut_remediation` to eliminate the attack path.
