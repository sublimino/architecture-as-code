# SFDP-P3-3 Go flush-path implementation

`signal-ingest` decorates the FrostDB object-store bucket. A successful upload
under `signaldb/observations/*/data.parquet` is hashed through an `io.TeeReader`,
then its object name, exact byte count, and lowercase SHA-256 are offered to a
bounded background attestation worker. Signing and publication never call
`InsertRecord` and never run while `FrostDBStore.Append` holds its mutex.

## Go APIs

```go
NewFrostDBStoreWithBucket(dir string, options ...FrostDBStoreOption)
WithSegmentAttestation(SegmentAttestorConfig{...})
WithManualFlush()
(*FrostDBStore).Flush(ctx)
(*FrostDBStore).WaitForAttestations(ctx)
NewSegmentAttestor(SegmentAttestorConfig{...})
(*SegmentAttestor).Status()
```

`Flush` rotates the active FrostDB block and waits only for the immutable
Parquet upload. `WaitForAttestations` is an observation seam for tests and
controlled shutdown; ingestion does not call it.

Each accepted segment produces:

- `segments.jsonl`, in the shared `signalloom.segment/v1` format;
- `attestations/%020d.dsse.json`, signed by the configured Ed25519 key;
- `checkpoints/%08d-<digest>.dsse.json`, one rolling checkpoint per processed flush;
- the atomically replaced protected high-water file;
- `segments.errors.jsonl` for signing, publication, immutable-reupload, and
  queue-overflow failures.

Identical object-name/digest/length reuploads are idempotent. A different byte
stream at an existing immutable object name is an explicit error. Queue
overflow records an error asynchronously and does not fail or wait in the
FrostDB upload path. Both the attestation queue and its secondary error queue
are bounded. If the secondary queue also overflows, `lost_error_count` is
persisted in protected high-water state so verification cannot report green
after an error record was lost. `Status` exposes both overflow counts, durable
error counts, and the worker's terminal processing error without feeding those
errors back through `Append`, `Upload`, or `Flush`.

Startup validates the journal tip and attestation/checkpoint inventories
against the protected high-water file before accepting work. Sequence numbers
come from journal order, never FrostDB's historical rotation identifiers, so a
rolled-back evidence directory cannot overwrite a newer protected high-water
state. At first protected-state creation, `historical_segments` captures the
existing Parquet inventory as a no-backfill baseline; later startup checks
accept that immutable baseline plus successfully journaled segments. A journal
`state=ok` record is appended only after its segment
attestation and rolling checkpoint are durable and any configured Archivista
publication has returned the matching content-addressed gitoid.

The evidence directory is append-only within this scope: journal records,
attestations, and checkpoints accumulate. Evidence compaction and retention
are deliberately deferred. Processing creates one checkpoint for each flush
that reaches the attestation worker; there is no automatic clock-driven flush
or checkpoint SLA.

## Environment wiring

Attestation is opt-in and applies only when `SIGNAL_STORE=frostdb`:

| Variable | Meaning | Default |
|---|---|---|
| `SIGNAL_SEGMENT_ATTESTATION=1` | Enable the decorator and worker | disabled |
| `SIGNAL_SEGMENT_EVIDENCE_DIR` | Journal, DSSE, and checkpoint directory | `SIGNAL_STORE_DIR` |
| `SIGNAL_SEGMENT_SIGNING_KEY` | PKCS8 Ed25519 private key | `$KEYS_DIR/witness.pem` |
| `SIGNAL_SEGMENT_HIGHWATER` | Protected freshness state | `$KEYS_DIR/signal-segment-highwater.json` |
| `SIGNAL_SEGMENT_QUEUE_SIZE` | Bounded successful-upload queue capacity | `16` |
| `ARCHIVISTA_URL` | Publish checkpoint DSSE to `<url>/upload` | file evidence only |
| `AUDIT_ANCHOR_REQUIRE_LOG=1` | Refuse startup without `ARCHIVISTA_URL` | disabled |

The key is the same `.keys/witness.pem` generated by `make signing-keys` and
used by the Python verifier. A configured Archivista returning an error,
non-2xx response, or empty response creates an explicit error record and does
not advance protected high-water state.

## Verification

```bash
cd d2-signalloom/apps/signal-ingest
LC_ALL=C LANG=C CGO_ENABLED=0 GOCACHE=/tmp/opencode/gocache \
  GOMODCACHE=/tmp/opencode/gomodcache go test ./...
LC_ALL=C LANG=C CGO_ENABLED=0 GOCACHE=/tmp/opencode/gocache \
  GOMODCACHE=/tmp/opencode/gomodcache go test -tags frostdb ./...
LC_ALL=C LANG=C CGO_ENABLED=0 GOCACHE=/tmp/opencode/gocache \
  GOMODCACHE=/tmp/opencode/gomodcache GOTMPDIR=/tmp/opencode/gotmp \
  go test -tags frostdb ./store -run '^$' \
  -bench '^BenchmarkFrostDBFlushAttestor$' -benchtime=100x -count=10
```

The FrostDB suite includes a cross-language test that generates real Parquet,
has the Python CLI accept the Go journal/checkpoint/DSSE/high-water set, mutates
the persisted bytes, and requires the Python verifier's divergence exit code 2.

## Measured count-10 benchmark

Measured 2026-09-05 on Linux/amd64, AMD Ryzen 9 7900X 12-Core Processor, using
Go 1.26.2 with `CGO_ENABLED=0`. The explicit latency budget is no more than
10% ingestion-visible flush-latency overhead for attestation enabled versus
disabled. The current worktree's toggled benchmark was run unchanged with 100
timed flushes per sample and ten samples per toggle:

```bash
cd d2-signalloom/apps/signal-ingest
LC_ALL=C LANG=C CGO_ENABLED=0 \
  GOCACHE=/tmp/opencode/gocache \
  GOMODCACHE=/tmp/opencode/gomodcache \
```

Benchstat found no statistically significant latency difference at its default
alpha of 0.05. The enabled median is about 1.6% lower than the disabled median,
so the observed result is inside the 10% overhead budget; it is not evidence
that enabling attestation improves performance.

The attestor runs asynchronously, so this benchmark measures ingestion-visible
flush latency, not background signing, publication completion, or a clock-based
checkpoint SLA. The fixed 100-iteration samples reduce the setup and scheduling
noise present in the obsolete `1x` evidence, but this is one workstation under
otherwise uncontrolled system load; it is not a production capacity result.
The benchmark source itself was untracked in this worktree during measurement,
so these numbers describe the measured worktree rather than a committed Git
revision.
