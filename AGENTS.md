# AGENTS.md — osramp-demo

Canonical agent onboarding doc. Read this first, then the per-slice AGENTS.md
for whichever D2 installation you're working on.

For the full documentation map, including the GCP lanes and the debugging
guides, see [`docs/README.md`](docs/README.md).

## Repository Purpose

Monorepo for the OSRAMP / Signal Loom demo platform. Hosts multiple independent
D2 delivery slices sharing a common Kind cluster foundation, Flux GitOps
control plane, and Envoy Ingress Gateway.

## Shared Foundation Stack

| Layer | Technology | Location |
|-------|-----------|----------|
| Cluster | Kind (single-node `osramp`) | `make up` / `make cluster` |
| GitOps | Flux Operator + ResourceSets | `d2-osramp-fleet/` |
| Ingress | Envoy Gateway (Gateway API, TLS) | `d2-infra/components/ingress/` |
| Registry | Zot (in-cluster, persistent `.cache/zot`) | `d2-osramp-fleet/local/zot.yaml` (`make registry`) |
| Signing | cosign + witness | `.keys/` (generated by `make signing-keys`) |
| Monitoring | kube-prometheus-stack + Grafana | `d2-infra/components/monitoring/` |
| Certs | cert-manager (self-signed cluster issuer) | `d2-infra/components/cert-manager/` |

Two services deploy **outside** their slice's `-up` target and are therefore easy
to miss. Both were finished, tested and undeployed for days:

| Service | Deploy | Consumed by |
|---------|--------|-------------|
| Fleet Manager | `make demo-signalloom-fleet-up` (applied directly, not via Flux) | `/fleet` in the dashboard, through nginx `/fleet-api/` |
| `afm-platform` | `make demo-k8s-afm-up` — opt-in; neither `make up` nor `demo-signalloom-up` brings it | `/rbac-analysis` and `/rbac-explorer`, plus seven nginx prefixes and the API's server-side `httpx` call |

`make demo-k8s-afm-up` builds its image from `$KUBESEC_AFM_ROOT`, not from
anything in this repo. The default is the **sibling of the repository root**,
`<repo>/../kubesec-afm` (`scripts/k8s-afm.sh:45`). On a machine without that
checkout it fails at `docker build`.

CAUTION: FROM A GIT WORKTREE THAT DEFAULT RESOLVES TO A PATH THAT DOES NOT
EXIST. A worktree lives outside the source checkout, so its parent holds no
`kubesec-afm`. Export the variable before you build:

```bash
export KUBESEC_AFM_ROOT=/path/to/kubesec-afm
```

`make gcp-tf-worktree-check` reports this, and
[`docs/gcp-demo/OPERATIONS.md`](docs/gcp-demo/OPERATIONS.md) explains the rest
of the worktree state a fresh checkout is missing.

Before adding a backend service of your own, read
[`docs/deploying-a-backend-service.md`](docs/deploying-a-backend-service.md): four
independent layers each break the page on their own, and none of them reports
"not deployed".

## Quick Start

```bash
# 1. Foundation: Kind cluster + Zot registry + signing keys + Flux
make up

# 2. Pick a demo slice (or combine them):
make demo-signalloom-up    # Signal Loom
make demo-osramp-up        # OSRAMP apps
make demo-k8s-afm-up       # KubeSec-AFM
make demo-olly-up           # Olly Sentinel
make demo-bao-up            # OpenBao/SPIRE only
make demo-agent-trust-up    # SPIFFE agent trust (needs inf-bao ready first)
make demo-cpai-up           # CPAI runtime
make demo-signalloom-fleet-up  # Fleet Manager — NOT included in demo-signalloom-up

# 3. Health check
make healthcheck            # foundation readiness
make doctor                 # full configured-cluster state report
```

## Shared Cluster Diagnostics

Run `make doctor` before investigating a cluster problem. `make doctor` and
`make cluster-debug` are equivalent, read-only entry points to the
comprehensive diagnostic report. It inspects cluster connectivity, unhealthy
pods, restart counts, warning events, Flux state, node metrics, and image-pull
failures. The detailed command-by-command runbook is in
[`TESTING.md`](TESTING.md#shared-cluster-diagnostics).

## The GCP estate — four lanes

The repository also runs on GCP, as four independent **lanes**: `demo-1`,
`demo-2`, `ci-1` and `ci-2`. Terraform provisions a lane; a separate step
builds the **estate** that runs on it. Every command takes `ENV=<lane>`.

```bash
make gcp-tf-up        ENV=demo-1              # plan, review, apply, write the hand-off
make gcp-tf-demo-up   ENV=demo-1              # deliver the code, build the estate, test it
make gcp-tf-ts-up     ENV=demo-1              # serve it on the tailnet; prints the URL
make doctor-node      ENV=demo-1              # node-level health for one lane
make doctor-node-all                          # every lane that has a hand-off file
make gcp-tf-destroy   ENV=demo-1 CONFIRM=demo-1
```

| Document | Read it for |
| :--- | :--- |
| [`docs/gcp-demo/RUNBOOK.md`](docs/gcp-demo/RUNBOOK.md) | Zero to a dashboard in a browser, step by step |
| [`docs/gcp-demo/OPERATIONS.md`](docs/gcp-demo/OPERATIONS.md) | The lanes, the health tooling, and the traps that misreport their cause |
| [`docs/gcp-demo/INCIDENTS-2026-08.md`](docs/gcp-demo/INCIDENTS-2026-08.md) | Five blockers, each with the measurement that found it |

The traps that cost the most time are in `OPERATIONS.md`. Four of them:

- `yes` emits `y`; `terraform destroy` needs exactly `yes`.
- `unset SSH_AUTH_SOCK` before any `gcloud compute ssh`, ad-hoc calls included.
- `make -n` executes any recipe line containing `$(MAKE)`, for real.
- Let's Encrypt allows five certificates per exact DNS name per 168 hours, and
  each lane holds its own clock.

## The older CI lane — two GCP VMs

This is a **separate system** from the four GCP lanes above. It predates them,
it uses its own VMs (`signalloom-ci`, `signalloom-ci-2`), and it is driven by
`scripts/ci/gcp-ci.sh` rather than by Terraform.

It runs the full e2e pipeline against a real cluster, on persistent VMs that
suspend between runs (~£0.02/day idle). `scripts/ci/vm-pipeline.sh` has 8
numbered stages and 27 stage reports once sub-stages are counted (`stage1b`
through `stage8b`). The full operating guide, including the traps that
misreport their own cause, is in [`scripts/ci/README.md`](scripts/ci/README.md).

| Command | What it does |
|---------|-------------|
| `make ci-gcp` | Warm run — reuses `signalloom-ci` |
| `make ci-gcp-2` | Second lane on `signalloom-ci-2` (cold only if you destroy the instance first) |
| `make ci-status` / `ci-status-2` | VM state |
| `make ci-ssh` / `ci-ssh-2` | SSH in for debugging (resumes if suspended) |
| `make ci-report` / `ci-report-2` | Last collected stage summary |

Three things that will otherwise cost you an hour each:

- **`SUSPENDED` is the SUCCESS state.** The script suspends on pass and leaves
  the VM RUNNING on failure for debugging. A suspended VM means the last run
  passed.
- **`unset SSH_AUTH_SOCK`** before any ad-hoc `gcloud compute ssh`, or it fails
  with `agent refused operation` — which surfaces during the provisioning wait
  and reads as a VM that never came up.
- **Never `gcp-ci.sh destroy` `signalloom-ci`.** It deletes the shared VPC, NAT
  and firewall that BOTH VMs use. Instance-only destroy is safe for
  `signalloom-ci-2`, which is how you get a genuinely cold run.

The two lanes hold **independent** locks (state lives on each VM), so warm and
cold can run concurrently; a refusal is that VM's own stale lock.

## Observing the demos

Prefer asking the cluster over reading the UI — these print what is *observably*
true, with the command that proved each claim:

| Command | Answers |
|---------|---------|
| `make doctor` | Full read-only cluster diagnostic |
| `make demo-signalloom-supercred-evidence` | Is the credential chain real? Six probes, each showing its command |
| `make demo-agent-trust-network-test` | Are the SPIFFE trust boundaries actually enforced? |
| `make demo-k8s-afm-status` | Is `afm-platform` up, and what does its `/health` say? |

"The page is broken" is not a diagnosis. Ask the path the browser actually uses,
from inside the pod that uses it — this distinguishes all four deployment layers
in one call:

```bash
kubectl -n fe-signalloom exec deploy/dashboard-signalloom -- \
  curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' \
  http://localhost:8080/fleet-api/v1/fleet/topology
# 200 application/json  → healthy
# 200 text/html         → no nginx location; the SPA answered the API call
# 504                   → NetworkPolicy, either the receiver's ingress or the caller's egress
# DNS failure           → the service is not deployed (make demo-signalloom-fleet-up)
```

`docs/cluster-debugging.md` §8 catalogues the probes that historically reported a
confident answer they had not earned — `nc` exit codes, unconfined new pods,
silent RoleBindings, and API paths that return `index.html` with 200 OK.
[`docs/deploying-a-backend-service.md`](docs/deploying-a-backend-service.md) is
the checklist that stops the last of those recurring.

## Pitfalls (Shared)

### Port-forward dies on pod rollout
Every `kubectl rollout restart` kills active port-forwards. Restart them after
any image rebuild + deploy cycle.

### Wait and readiness semantics — use the shared helpers, never `sleep`

`scripts/lib/wait.sh` is the canonical polling library and every script and
bats suite should use it. It gives existence-first semantics, exponential
backoff with jitter, and `WAIT_STAT` telemetry — all of which a bare
`sleep 5` throws away. It also avoids the cold-cluster race where
`kubectl wait` errors instantly against an object that doesn't exist yet.

Source it, then pick the helper that matches what you are actually waiting for:

| Helper | Use for |
|---|---|
| `wait_rollout <deploy> [-n ns] [deadline]` | **Deployments.** Wraps `kubectl rollout status`. |
| `wait_pods_ready <selector> [-n ns] [deadline]` | Pods by label. Requires ≥1 match AND none not-ready. |
| `wait_k8s_ready <kind> <name> [-n ns] [--for cond] [deadline]` | Pods, Jobs, Flux objects. Existence-first, then `kubectl wait`. |
| `wait_flux_ready <kind> <name> [-n ns] [deadline]` | Flux `Kustomization` / `ResourceSet` Ready. |
| `wait_reachable <url> [deadline]` | An HTTP endpoint answering. |
| `wait_tcp <host> <port> [deadline]` | A port accepting connections. |
| `_wait_retry <deadline> <label> <cmd>` | Generic backoff when nothing above fits. |

**The trap: `wait_k8s_ready` defaults to `--for=condition=ready`, and a
Deployment has no `Ready` condition.** Deployments expose only `Available`,
`Progressing` and `ReplicaFailure`, so `kubectl wait --for=condition=ready
deployment/x` times out *even against a perfectly healthy Deployment*. Use
`wait_rollout` for Deployments. This shipped in `scripts/supercred-demo.sh`
and failed the SuperCred preflight closed against a 1/1, `Available=True`
OpenBao that had been running 17 hours, telling the operator to run
`make demo-signalloom-up` on a cluster where it had already been run — which
in turn left six SUPERCRED bats tests permanently red for want of a
deployment that could never be created (found 2026-08-02, fixed in `10f1713`).

Corollary, and the reason this sits in Pitfalls: **a wait that can never
succeed and a gate that always passes are the same bug wearing different
hats.** Both look like a check and neither is one. The same day produced
`readyExpr: status.observedGeneration >= 0` (trivially true the instant an
object exists, so it gated nothing) and a `substituteFrom` whose missing keys
are a silent no-op. When you write a wait or a gate, prove it fails when it
should — inject the bad state and watch it go red.

For **Playwright**, the equivalent rule is: use web-first assertions
(`await expect(locator).toBeVisible()`), `waitForResponse` and
`waitForLoadState`. Never use `page.waitForTimeout(n)` as a readiness
mechanism — it passes on a fast box and fails under load.

### Mutable `:latest` tag with `imagePullPolicy: IfNotPresent`
After `kind load docker-image`, verify the pod picked up the new image:
```bash
kubectl get pod <name> -n <ns> -o jsonpath='{.status.containerStatuses[0].imageID}'
```
If stale, `kubectl delete pod <name>` forces re-resolve.

### Worktree location
Worktrees go in `~/src/.worktrees/<repo>/<branch>/`, never inside the repo.
In-repo `worktrees/` directories bleed into bun/find/rg/test-runners.

### Zot cache persistence
`.cache/zot/` survives `make down` (intentional — avoids re-pulling). Use
`make zot-cache-reset` to clear it.

### Flux variable substitution
`postBuild.substituteFrom` on a Flux Kustomization runs envsubst over the
**entire rendered manifest text**, not just specific fields — every string
scalar is in scope, including a ResourceSet's `spec.inputs` as much as its
`spec.resources`. Don't assume `${VAR}` "can't reach" some nested field; if
it's in the path a Kustomization with `postBuild` reconciles, it's reached.

The real risk is a **first-reconcile race**, not substitution scope.
`clusters/<env>/tenants.yaml` and `clusters/<env>/flux-system/runtime-info.yaml`
(the ConfigMap it substitutes from) are both applied by the same top-level
`flux-system` Kustomization in one batch. Without an explicit `dependsOn`,
`tenants`'s very first reconcile can fire before kustomize-controller's own
client has observed the ConfigMap, find no value for e.g. `${ARTIFACT_TAG}`,
and leave it as a literal string. Missing `substituteFrom` keys are a
**silent no-op, not an error**, so Flux marks the apply `Ready=True` anyway —
nothing then retries, and the bug sits there indefinitely (found live
2026-08-02: cert-manager/ingress/monitoring/trivy-system all failed with a
literal `${ARTIFACT_TAG}` in their OCIRepository tag, hours after bootstrap).
Fix: `clusters/<env>/tenants.yaml` carries `dependsOn: [{name: flux-system}]`
so it can't attempt substitution until the Kustomization that creates
`flux-runtime-info` is confirmed `Ready=True`. Any new Kustomization that
reads `postBuild.substituteFrom` on a ConfigMap/Secret it doesn't itself own
needs the same `dependsOn` guard if it's applied in the same batch as its
source.

If you hit this class of bug live (literal `${VAR}` in a resolved manifest,
or `flux get all -A --status-selector ready=false` showing `MANIFEST_UNKNOWN`
/ `kustomization path not found` with a URL-encoded `${...}` in the message):
it's almost always stale, not broken — `flux reconcile kustomization tenants
-n flux-system --with-source` forces a fresh render against the *current*
ConfigMap and resolves it immediately, no source change required. That's a
live-cluster workaround, not a fix — still land the `dependsOn` (or
equivalent ordering) so it can't recur on the next bootstrap.

ResourceSets activated via `kubectl patch resourceset <name> --type merge`
(`apps`, `olly`, `signalloom-infra`, `signalloom-apps`, via the
`demo-<slice>-up` scripts) are immune: their `spec.inputs` in
`tenants/base/*.yaml` ships as a literal `[]`, and the activation script
injects concrete values directly — that path never goes through envsubst.
Only inputs declared inline with `${VAR}` in a base ResourceSet (currently
just `d2-osramp-fleet/tenants/base/infra.yaml`) are exposed to this race.

**Annotation convention** — every `kustomization.yaml` and any other Flux
resource YAML containing `${VAR}` carries a `# FLUX ENVSUBST:` header stating
whether Flux substitutes it, using one of:
- `YES` — a Flux Kustomization with `postBuild.substituteFrom` reaches this
  file/manifest.
- `NO` — the Flux Kustomization reconciling this directory has no
  `postBuild`; any `${VAR}` here is the workload's own runtime expansion
  (e.g. SPIRE's `-expandEnv`), not Flux's.
- `N/A` — applied outside Flux (`kubectl apply`/`kubectl patch`) entirely.
- `FLEET` — a fleet overlay (`tenants/*/kustomization.yaml`) processed by the
  `tenants` Kustomization itself, not a workload kustomization.
Get this right and accurate, not just present — the annotation exists
because a field templated where substitution doesn't reach (or is assumed
reached and isn't) is exactly how this incident happened.

## Conventions

- **Commits**: conventional commits with slice scope — `feat(signalloom):`, `fix(osramp):`, `test(k8s-afm):`
- **Signing**: all images and OCI artifacts are cosign-signed, and Flux refuses to
  reconcile an unsigned one — that half is machine-enforced. Commit GPG signing is
  the intent but is **not** enforced and the history is unsigned (`git log
  --pretty='%h %G? %s'` reports `N` on all of the last 200 commits). Match the
  branch you are on rather than assuming: a bare `git commit` on a branch whose
  history is unsigned launches pinentry against a tty the agent harness cannot
  reach and blocks until timeout — use `--no-gpg-sign` there.
- **Supply chain**: SBOM (SPDX), SLSA provenance, digest verification
- **Everything signed**: nothing deploys unsigned, even locally
- **Tests ship with code**: new features include unit + integration + acceptance coverage
