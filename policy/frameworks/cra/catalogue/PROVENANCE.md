# Provenance of the EU-act extracts

Three extracts, one per act cited by the `cra`, `dora` and `nis2` packs. Each
is generated by `./extract.sh`, and none is hand-edited.

| Extract | Act | CELEX | Divisions | Articles |
|---------|-----|-------|----------:|---------:|
| `eu-2024-2847-cra.tsv` | Regulation (EU) 2024/2847 (Cyber Resilience Act) | `32024R2847` | 85 | 71 |
| `eu-2022-2554-dora.tsv` | Regulation (EU) 2022/2554 (DORA) | `32022R2554` | 64 | 64 |
| `eu-2022-2555-nis2.tsv` | Directive (EU) 2022/2555 (NIS 2) | `32022L2555` | 49 | 46 |

Generated 2026-10-10. CRA's 85 = 71 articles + 8 annexes + 6 annex parts
(Annex I Parts I-II, Annex VIII Parts I-IV). DORA has no annexes. NIS2's 49 =
46 articles + Annexes I-III.

## Source and how to fetch it

The publisher's Cellar endpoint, **not** `eur-lex.europa.eu`:

```
http://publications.europa.eu/resource/celex/<CELEX>
  Accept:          application/xhtml+xml
  Accept-Language: eng
```

Two traps, both of which produce something that looks like a different problem
than it is:

1. **EUR-Lex's HTML endpoints answer a non-browser client with HTTP 202 and
   zero bytes.** Not a redirect, not a 403 — an empty success. A fetch that
   reads as "the document is empty" is actually "you are not a browser".
2. **Cellar requires `Accept-Language` as well as `Accept`.** Without it the
   service returns **HTTP 400** with
   `Invalid content type CONTENT_STREAM for WORK [...] without language`,
   which reads like a complaint about the `Accept` header and is not. Adding
   `notice=branch` or similar to the `Accept` value instead produces
   `Illegal accept header`, which sends you further the wrong way.

Requesting the resource without any `Accept` header returns RDF/XML metadata
about the work — a valid 200 with none of the legal text in it. That is the
quietest of the three failures, because it succeeds.

## What is extracted, and why not by pattern-matching

`extract.py` keys on the publisher's own semantic CSS classes:

| Class | Carries |
|-------|---------|
| `oj-ti-art` | the article number, e.g. `Article 6` |
| `oj-sti-art` | the article heading, e.g. `ICT risk management framework` |
| `oj-doc-ti` inside `eli-container id="anx_*"` | annex number, then annex heading |
| `oj-ti-grseq-1` | an annex Part heading |

Articles appear in strict `oj-ti-art` / `oj-sti-art` pairs, so pairing is
mechanical rather than inferred. `extract.py` exits non-zero if the pairing
breaks or if the article count differs from the value `extract.sh` asserts.

**Pattern-matching the prose would be wrong, and measurably so.** A regex for
`^Article N$` over the rendered text of NIS2 finds **73** apparent articles
where there are 46. **Annex III of NIS2 is a correlation table** whose
cells are article references. The first attempt at this extract made that
exact error. The markup does not have that failure mode.

Headings are normalised only for whitespace: the source uses NO-BREAK SPACE
(U+00A0) inside `Article 6` and `ANNEX I`, which nobody writing a citation
would type.

## What the extract does and does not support

It resolves **divisions**: an article, an annex, or an annex Part. It has no
row for a paragraph, point or sub-point, so `anchor-test.sh` anchors
`Annex I Part II point (1)` as far as `Annex I Part II`. Point-level text is
quoted verbatim in each pack's README so a reviewer can check the remainder
against the act directly.

It cannot tell whether a citation is the *right* one. That is judgement and
lives in each pack's README under "Evidence or proxy".

## Regeneration

```sh
./extract.sh      # fetches all three acts, rewrites all three .tsv files
./anchor-test.sh  # every citation resolves, every stated heading matches
./run-tests.sh    # anchor + pricing
```

`extract.sh` needs `curl` and `python3`, while the tests need `jq` and `awk`
only. Commit any regeneration that changes an extract together with the README
or citation it forces to change. The anchor test fails otherwise, which is the
point.
