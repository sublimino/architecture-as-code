This operational runbook provides security operators, incident responders, and compliance engineers with definitive procedures for observing, analyzing, and governing autonomous coding agents detected across the enterprise estate.

:::caution[Strict Operational Boundary: No Developer Productivity Tracking]
Signal Loom detective telemetry exists **exclusively for security governance, agent inventory attribution, and compliance auditing**. 

Under no circumstances shall this telemetry be used to evaluate, rank, score, or infer individual developer productivity, working hours, speed, or performance. Attempting to use token throughput, step counts, tool frequencies, or session durations for performance management violates the [GDPR Lawful Basis Assessment](/docs/reference/lawful-basis-assessment/) and enterprise Works Council co-determination agreements.
:::

## 1. What a Security Operator Sees in the Dashboard

When an autonomous coding agent executes on an enrolled host, the **Signal Loom Dashboard** surfaces the agent under **Agents → Workstation Coding Agents** (`/agents?tab=coding-agents`) and within the **Agent Trust Topology** (`/topology`).

### 1.1 Coding Agent Telemetry Card Layout
Each detected agent session renders as an interactive card displaying:

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│  [🤖 Claude Code]   ses_9b4e182a-4c2f-4a12-881b-a19283f019a2        [STATUS: ACTIVE ●]           │
│  Host: ws-lon-sec-418   PID: 819201   PPID: 819150   User: andy   Comm: claude                   │
│                                                                                                  │
│  📋 Kanban Task: SLCD-P6-2 (implementation)                ⏱️ Duration: 14m 28s                  │
│  🧠 Model Family: claude-3-7-sonnet                         🌐 Endpoint: api.anthropic.com       │
│  📊 Throughput: 125,400 tokens in / 4,820 tokens out        👣 Steps: 18                          │
│                                                                                                  │
│  🔧 Tool Execution Breakdown:                                                                    │
│  [view_file: 14] [replace_file_content: 6] [run_command: 4] [grep_search: 2] [other: 0]          │
│                                                                                                  │
│  🛡️ Zero Customer Payload Invariant: CERTIFIED (No code, prompt, or secret text collected)       │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 Key Telemetry Fields Explained
- **Harness & Session ID**: The classified agent runtime family and its unique session UUID.
- **Process Context**: Process ID (`pid`), parent process ID (`ppid`), binary command name (`comm`), and host identifier.
- **Kanban Task Strip**: Correlated task identifier, mission shortcode, role (`implementation`, `governor`, `preflight`), and elapsed execution time.
- **Token & Step Counters**: Aggregate token consumption (`tokens_in`, `tokens_out`) and agent reasoning turn iterations (`step_count`).
- **Tool Histogram**: Distribution of executed tools across normalized categories (`view_file`, `write_to_file`, `replace_file_content`, `run_command`, `grep_search`, `list_dir`, `ask_question`, etc.).
- **Inference Endpoint**: Attributed external LLM endpoint hostname derived via socket netlink attribution.

## 2. Interpreting Harness Classifications

The classifier engine categorizes detected processes into 7 canonical harness families:

| Harness Name | Typical Binary `comm` | Primary Model Provider | Typical Workstation Role |
|---|---|---|---|
| `claude` | `claude`, `node` | Anthropic (`api.anthropic.com`) | Autonomous agentic coding & refactoring |
| `antigravity` | `antigravity`, `agy` | Google (`generativelanguage.googleapis.com`) | Multi-agent pair programming & CLI tool loops |
| `codex` | `codex`, `codex-exec` | OpenAI (`api.openai.com`) | Sandboxed execution & code synthesis |
| `cpai` | `cpai`, `kpai`, `omp` | Multi-provider / OpenBao | Governed CPAI swarms & mission execution |
| `opencode` | `opencode` | Local / Ollama / OpenAI | Open-source autonomous agent loops |
| `hermes` | `hermes` | Multi-model agent runtime | Iterative research & terminal automation |
| `aider` | `aider`, `python3` | Multi-model / LiteLLM | In-terminal git-paired coding assistant |

## 3. Interpreting Confidence Scores

Every telemetry record carries a classification confidence score:

### `high` (High Confidence)
- **Criteria**: Multiple independent signals match the same harness. For example, binary `comm` is `claude`, process cgroup path contains `.claude`, active network socket connects to `160.79.104.0/23` (`api.anthropic.com`), and an active transcript is open.
- **Operator Action**: Normal operation. No manual triage required.

### `medium` (Medium Confidence)
- **Criteria**: A strong primary signal exists (e.g. binary basename matches `codex`), but secondary signals are incomplete (e.g. network socket is transient or not yet established).
- **Operator Action**: Monitor lifecycle. Verify the agent correlates with an expected developer task.

### `low` (Low Confidence)
- **Criteria**: A generic runtime (e.g. `node`, `python3`, `bun`) is operating inside an isolated cgroup or tmux session with active network egress to a known inference CIDR, but no distinctive harness binary name or transcript schema was matched.
- **Operator Action**: Review Kanban task attribution and endpoint hostname. Check if the developer is using an unlisted harness wrapper.

### `unknown` (Unknown Classification)
- **Criteria**: An active process establishes persistent network connections to an inference provider or exhibits agentic tool execution cycles, but matches zero known harness signatures.
- **Operator Action**: **Requires operator triage** following Section 4 below.

## 4. Unknown Classification Triage Procedure

When an agent record appears with classification `unknown`, follow this step-by-step triage runbook:

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│                               UNKNOWN CLASSIFICATION TRIAGE STEPS                                │
│                                                                                                  │
│ [Step 1: Check Egress] ──> [Step 2: Inspect Cgroup] ──> [Step 3: Check Kanban] ──> [Decision]    │
│  (Verify provider)          (Parent process/unit)        (Task correlation)         (Resolve/Act)│
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Step 1: Check Egress Destination & Port
1. Inspect the `network.inference_endpoint` field in the telemetry record.
2. Cross-reference the destination with the [Inference Provider CIDR Reference](/docs/reference/inference-provider-ranges/):
   - Is it an approved corporate model endpoint (e.g. `api.anthropic.com`, Google Vertex)?
   - Is it an unapproved third-party or unauthorized proxy endpoint?
3. If egress targets an unapproved external IP, escalate immediately to Security Incident Response.

### Step 2: Inspect Process Cgroup & Parent Context
1. Query the host sensor diagnostic status or inspect the host's systemd unit/cgroup structure.
2. Identify the parent launcher (e.g. VS Code, Cursor, JetBrains, terminal shell, automated CI job).
3. **Privacy Boundary**: Do NOT inspect developer files, prompt logs, or raw `/proc/<pid>/cmdline` strings. Identify the tool identity through binary executable basenames and systemd unit names only.

### Step 3: Check Kanban Task Correlation
1. Inspect the `kanban.task_id` and `kanban.role` fields.
2. If a valid task ID is present (e.g. `SLCD-P6-2`), verify against the team's project board to confirm an authorized work item is in progress.
3. If the agent is running outside any tracked Kanban task, determine whether the developer is running an interactive experimental session.

### Step 4: Resolution & Governance Action
- **Case A: Approved New Tool**: If the process is a legitimate newly adopted coding tool, submit a request to add its binary signature to `d2-signalloom/apps/agentmaxxing-host-sensor/classifier.py`.
- **Case B: Shadow / Unapproved AI Agent**: Contact the workstation user to align on corporate AI usage policies.
- **Case C: Rogue or Compromised Process**: If the process exhibits suspicious persistence, unauthorized egress, or evasion tactics, immediately initiate containment:
  - Refer to the [Agent Containment & Response Operational Runbook](/docs/operate/containment-runbook/).
  - Trigger multi-plane isolation via API:
    ```bash
    curl -X POST https://dashboard.osramp.acme.local/api/v1/fleet/contain \
      -H "Authorization: Bearer $OPERATOR_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{"target_ref": "host:ws-lon-sec-418/pid:819201", "reason": "unauthorized_shadow_agent"}'
    ```
