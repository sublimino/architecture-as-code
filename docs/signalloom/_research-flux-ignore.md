# Flux field-ignore mechanisms — research against the running cluster

> Every result below is **measured on `kind-osramp` on 2026-08-03**, not recalled from upstream docs.
> Where a feature does not exist in the running version, that is stated plainly rather than described
> from a newer upstream release.
> Companion analysis: `docs/signalloom/stun-under-flux.md` — this file answers its **Q1**.
> All experiments were reversible; §7 records the restoration check.

## TL;DR

1. The field the brief asked about — `.spec.driftDetection.ignore` on Kustomization — **does not exist**
   in this version. The correct field is **`.spec.ignore`**, and it does exactly what is needed.
2. **`.spec.ignore` works, and it is the only mechanism that does.** Measured: the stun label survives
   repeated reconciles while every other field on the pod stays fully drift-corrected.
3. **It only protects a path the manifest actually declares.** Deleting the literal `idle` from the
   manifest does *not* fix this — it makes it worse (the label is wiped entirely). The literal must
   **stay**, and be ignored. This is counter-intuitive and is the single most important finding here.
4. **flux-operator v0.57.0 has no equivalent.** ResourceSet has no `ignore`, no `patches`, no
   `driftDetection`, and it **ignores every per-object annotation** — including
   `kustomize.toolkit.fluxcd.io/ssa: ignore` and `fluxcd.controlplane.io/reconcile: disabled`. The
   second declaration cannot be fixed in place; the object has to move or the state has to live
   elsewhere.
5. The stun's two **annotations** (`stunned-at`, `stun-reason`) are wiped by default and need the same
   declare-then-ignore treatment as the label. Fixing only the label leaves the demo half-broken.

## 2. Mechanism inventory — what exists in THIS version

### 2.1 `.spec.ignore` on Kustomization — **EXISTS. This is the per-field drift-ignore.**

**Correction to the brief:** the field is `.spec.ignore`, not `.spec.driftDetection.ignore`.

```
$ kubectl get crd kustomizations.kustomize.toolkit.fluxcd.io -o json | <list spec keys>
=== version v1 ===
top-level spec keys: buildMetadata, commonMetadata, components, decryption, deletionPolicy,
  dependsOn, force, healthCheckExprs, healthChecks, ignore, ignoreMissingComponents, images,
  interval, kubeConfig, namePrefix, nameSuffix, patches, path, postBuild, prune, retryInterval,
  serviceAccountName, sourceRef, suspend, targetNamespace, timeout, wait
driftDetection: ABSENT
```

```
$ kubectl explain kustomization.spec.driftDetection
error: field "driftDetection" does not exist

$ kubectl apply --dry-run=server --validate=strict -f probe-kust-drift.yaml
Error from server (BadRequest): Kustomization in version "v1" cannot be handled as a Kustomization:
  strict decoding error: unknown field "spec.driftDetection"
```

`.spec.driftDetection.ignore` **does** exist — on **HelmRelease**, not Kustomization. Both use the same
`IgnoreRule` type, which is why they get conflated. Nothing in the Signal Loom path is a HelmRelease,
so it is not applicable here.

Exact schema of `Kustomization.spec.ignore`, from the running CRD:

```json
{
  "description": "Ignore is a list of rules for specifying which changes to ignore\nduring drift detection. These rules are applied to the resources managed\nby the Kustomization and are used to exclude specific JSON pointer paths\nfrom the drift detection and apply process.",
  "type": "array",
  "items": {
    "description": "IgnoreRule defines a rule to selectively disregard specific changes during\nthe drift detection process.",
    "type": "object",
    "required": ["paths"],
    "properties": {
      "paths": {
        "description": "Paths is a list of JSON Pointer (RFC 6901) paths to be excluded from\nconsideration in a Kubernetes object.",
        "type": "array",
        "items": {"type": "string"}
      },
      "target": {
        "description": "Target is a selector for specifying Kubernetes objects to which this\nrule applies.\nIf Target is not set, the Paths will be ignored for all Kubernetes\nobjects within the manifest of the Kustomization.",
        "type": "object",
        "properties": {
          "group": {...}, "version": {...}, "kind": {...},
          "name": {...}, "namespace": {...},
          "labelSelector": {...}, "annotationSelector": {...}
        }
      }
    }
  }
}
```

`kubectl explain` agrees:

```
$ kubectl explain kustomization.spec.ignore --recursive
FIELD: ignore <[]Object>
FIELDS:
  paths	<[]string> -required-
  target	<Object>
    annotationSelector	<string>
    group	<string>
    kind	<string>
    labelSelector	<string>
    name	<string>
    namespace	<string>
    version	<string>
```

Two phrases in that description are decisive: **"JSON Pointer (RFC 6901)"** (a single label key is
addressable) and **"from the drift detection *and apply* process"** (the path is excluded from the apply,
not merely from the diff).

### 2.2 `kustomize.toolkit.fluxcd.io/ssa` — object-level annotation, measured

Values were tested by injecting the annotation into the *desired* manifest via `.spec.patches` —
necessary because kustomize-controller reads this annotation from the manifest, not from the live object.
Annotating the live pod does nothing.

| Value | Stun label preserved? | Rest of pod still managed? |
|---|---|---|
| (unset, default) | **No** — reverted to `idle` | Yes |
| `merge` | **No** — reverted to `idle` | Yes |
| `ignore` | Yes | **No** — whole object unmanaged |

`merge` does **not** solve this. It relaxes conflict-forcing, but kustomize-controller still re-applied
the declared `idle` and took ownership back from `kubectl-label`. Measured, §4 case B.

`ignore` works but at whole-object cost: in the same test the control field `signalloom.ai/model` was
left at `TAMPERED` and ownership passed to `kubectl-label`. For a pod whose *entire demo purpose* is that
its missing `securityContext` gets caught by the compliance scan, silently un-managing it is a poor trade.

### 2.3 `kustomize.toolkit.fluxcd.io/reconcile: disabled` — object-level

Measured identical to `ssa: ignore`: the label survives, and the rest of the object stops being
reconciled (`model` stayed `TAMPERED`). It stops **drift correction and re-apply**, not creation — the
object is created on first apply and then left alone. Whole-object blast radius; wrong granularity for
one label.

This annotation family is already in use in the repo — `kustomize.toolkit.fluxcd.io/force: "true"` at
`d2-signalloom/infra/inf-bao/configs/base/openbao-supercred-bootstrap.yaml:16` and
`kustomize.toolkit.fluxcd.io/prune=disabled` at `scripts/supercred-demo.sh:150` — so it is known-honoured
by this controller on the Kustomization path.

### 2.4 `.spec.patches` to remove the field before apply — **actively harmful here**

The intuitive fix is to strip the literal:

```yaml
spec:
  patches:
    - target: {kind: Pod, name: agent-cardvault}
      patch: |
        - op: remove
          path: /metadata/labels/signalloom.ai~1state
```

**Measured result: the label is deleted, and the stun is then wiped on every reconcile** (§4 case D,
re-run in isolation with pod UID tracking to rule out recreation — same UID throughout, three
consecutive reconciles, label empty every time). This is worse than the status quo: instead of the
dashboard showing a stale `idle`, it shows *nothing*.

It is also brittle. `op: remove` on an absent path fails the whole build:

```
Ready=False BuildFailed: kustomize build failed: error in remove for path:
  '/metadata/labels/signalloom.ai~1state': Unable to remove nonexistent key:
  signalloom.ai/state: missing value
```

So the patch is coupled to the base manifest — remove the literal upstream and the Kustomization breaks.

### 2.5 SSA field ownership and `force`

`Kustomization.spec.force` is **not** SSA force-ownership:

```json
"force": {
  "default": false,
  "description": "Force instructs the controller to recreate resources\nwhen patching fails due to an immutable field change.",
  "type": "boolean"
}
```

`fe-signalloom/apps` has `force: true`. Worth flagging separately: a failed patch on that pod causes a
**delete-and-recreate**, which is a second, independent way the stun evidence disappears — and a pod
restart is visible to the audience.

SSA force-*conflicts* is a separate, always-on behaviour of the apply. The managedFields dump in §1a is
the proof: the `kustomize-controller` Apply entry lists `f:signalloom.ai/state`, so it holds the field,
and an imperative `kubectl label` is overwritten on the next apply.

### 2.6 flux-operator ResourceSet — **no per-field ignore exists, and annotations are ignored**

```
$ kubectl get crd resourcesets.fluxcd.controlplane.io -o json | <list spec keys>
=== ResourceSet version v1 served true storage true ===
spec keys: commonMetadata, dependsOn, inputStrategy, inputs, inputsFrom,
           resources, resourcesTemplate, serviceAccountName, steps, wait
```

```
$ kubectl apply --dry-run=server --validate=strict -f probe-rs-ignore.yaml
Error from server (BadRequest): ResourceSet in version "v1" cannot be handled as a ResourceSet:
  strict decoding error: unknown field "spec.ignore"

$ kubectl apply --dry-run=server --validate=strict -f probe-rs-patches.yaml
Error from server (BadRequest): ResourceSet in version "v1" cannot be handled as a ResourceSet:
  strict decoding error: unknown field "spec.driftDetection", unknown field "spec.patches"
```

Stated plainly: **`ignore`, `patches` and `driftDetection` do not exist on ResourceSet in flux-operator
v0.57.0.** And per-object annotations do not help either — measured in §5, flux-operator reverted every
single variant.

## 3. Recommendation

### For declaration 1a (`agents-cardvault.yaml` → Kustomization) — use `.spec.ignore`

Ranked, with measured evidence:

| Rank | Mechanism | Label survives | Rest managed | Verdict |
|---|---|---|---|---|
| **1** | **`.spec.ignore` with JSON pointers** | **Yes** | **Yes** | **Recommended** |
| 2 | `kustomize.toolkit.fluxcd.io/reconcile: disabled` | Yes | No | Fallback only; un-manages the pod |
| 3 | `kustomize.toolkit.fluxcd.io/ssa: ignore` | Yes | No | Same cost as #2, no benefit |
| 4 | `kustomize.toolkit.fluxcd.io/ssa: merge` | No | Yes | Does not solve the problem |
| 5 | `.spec.patches` `op: remove` | No — **wiped** | Yes | Worse than status quo; brittle |
| — | `spec.suspend` on the Kustomization | Yes | No (everything) | Rejected in `stun-under-flux.md` §4 |

`.spec.ignore` is the only row that gets both columns right. Concretely, on `Kustomization
fe-signalloom/apps`:

```yaml
spec:
  ignore:
    - target:
        kind: Pod
        labelSelector: signalloom.ai/agent=true
      paths:
        - /metadata/labels/signalloom.ai~1state
        - /metadata/annotations/signalloom.ai~1stunned-at
        - /metadata/annotations/signalloom.ai~1stun-reason
```

**And — non-negotiable — the manifest must keep declaring all three paths.** `agents-cardvault.yaml`
already declares the label; it must additionally declare the two annotations with placeholder values:

```yaml
  annotations:
    signalloom.ai/stunned-at: ""
    signalloom.ai/stun-reason: ""
```

Without those two lines the annotations are wiped on every reconcile even with the ignore rule in place.
See §6 for why.

Scoping `target` by `labelSelector: signalloom.ai/agent=true` rather than bare `kind: Pod` keeps the rule
from applying to unrelated pods in the same Kustomization. (Both were tested; `kind: Pod` works, the
selector is defence in depth.)

### For declaration 1b (`signalloom.yaml` → ResourceSet) — nothing works in place

No mechanism in flux-operator v0.57.0 fixes this. Options, ranked:

1. **Move the agent-inventory pods out of the ResourceSet into a Kustomization** that carries the same
   `.spec.ignore` rule. One mechanism across both paths, keeps the pods under GitOps management, and the
   ignore rule is already proven. Cost: a manifest move, and `signalloom-infra`'s namespace/RBAC
   resources should stay where they are.
2. **Stop storing runtime state on Flux-managed objects.** Have the stun write to an object the runtime
   owns — a ConfigMap or CR in a namespace no Kustomization or ResourceSet manages — and have the proxy
   read state from there, falling back to the pod label. Architecturally the right answer (it removes the
   category error rather than working around it) and it makes the whole `.spec.ignore` question moot. Cost:
   changes `server.py` discovery and the dashboard's source of truth.
3. **Drop `agent-sir-lancelot` from Flux entirely**, as the other four inventory agents already are
   (`signalloom-agents.sh`). Cheapest, least principled, and it weakens the "the fleet is GitOps-managed"
   story the demo is making.

**Recommendation: (1) now, (2) as the real fix.** (1) is a same-day change that makes both declarations
behave identically under one mechanism, which is worth a lot for a demo that has to survive a live
audience. (2) is what should land before this pattern is shown to a bank as a reference architecture —
`stun-under-flux.md` §7.2 is already making that argument, and the measurements here strengthen it: the
evidence channel is not merely reverted, it is *deleted*, and the dashboard cannot distinguish "never
stunned" from "stun wiped".

**Do not** reach for `spec.suspend`, `fluxcd.controlplane.io/reconcile: disabled` on the ResourceSet, or
the reconciler pin the e2e harness uses. All three have a blast radius far larger than the threat, and
`stun-under-flux.md` §4 already argues the pin is a *source* of demo failure.

## 6. The rule that explains every result: **ignore only protects a DECLARED path**

The `op: remove` result and the annotation-wipe result initially looked contradictory. They are not.
A second probe isolated the behaviour:

```
OBJECT                         label     annot     verdict
probe-g-labels-declared        ''        ''        WIPED   (labels block declared, state key absent)
probe-h-no-labels-block        ''        ''        WIPED   (no labels block at all)
probe-i-annotation-target      ''        ''        WIPED   (annotation, none declared)
```

So Flux removes a label or annotation key added by another manager on an object it manages, **even keys
it never declared** — on both controllers. Simply not declaring the field does not leave it free.

And on the Kustomization path, the ignore rule protected the label in every shape tested but **never**
protected the annotations:

```
=== A: label path only (annotations NOT tampered) ===        state='stunned'  annotations WIPED
=== B: label path only, annotations ALSO tampered ===        state='stunned'  annotations WIPED
=== C: three paths in ONE rule ===                           state='stunned'  annotations WIPED
=== D: three SEPARATE rules, one path each ===               state='stunned'  annotations WIPED
=== E: two paths — label + ONE annotation ===                state='stunned'  annotations WIPED
=== F: whole maps /metadata/labels + /metadata/annotations === state='stunned'  annotations WIPED
```

The difference between the label and the annotations is that **the manifest declares the label and does
not declare those annotations.** Hypothesis: `.spec.ignore` works by substituting the *live* value at
each ignored path into the desired object before applying — which requires the path to exist in the
desired object. A path the manifest never declares cannot be substituted, so it is left out of the apply
and the API server drops it.

Tested directly, by declaring placeholder annotations in the manifest (injected via `.spec.patches`) and
ignoring the same paths:

```
=== TEST G: placeholder annotations DECLARED in manifest + ignore on those paths ===
  after placeholders applied:
    signalloom.ai/stun-reason=''
    signalloom.ai/stunned-at=''
  now stun:
    state='stunned' stunned-at='2026-08-03T18:00:00Z' stun-reason='compliance-failure'
  reconcile #1:
    state='stunned' stunned-at='2026-08-03T18:00:00Z' stun-reason='compliance-failure'
  reconcile #2:
    state='stunned' stunned-at='2026-08-03T18:00:00Z' stun-reason='compliance-failure'

  HYPOTHESIS CONFIRMED? label + BOTH annotations survive: YES

=== TEST H: same placeholders DECLARED but ignore rule REMOVED (control) ===
  before reconcile: state='stunned' stunned-at='2026-08-03T18:00:00Z' stun-reason='compliance-failure'
  after reconcile:  state='idle'    stunned-at=''                     stun-reason=''
  -> CONFIRMED (all reverted)
```

Confirmed with a matched control. **The literal must stay in the manifest and be ignored.** Declaring
the field and ignoring it is the mechanism; deleting the field defeats it.

This also explains a behaviour worth knowing about: **a freshly created pod gets the manifest's literal.**
Deleting `agent-cardvault` with the ignore rule active and letting Flux recreate it produced
`signalloom.ai/state=idle` on the new pod. That is the desired behaviour — a new agent starts `idle` and
is frozen at whatever the runtime sets thereafter — but combined with `spec.force: true` (§2.5) it means a
pod recreation still clears a stun.

### JSON pointer escaping — and a silent-failure trap

`~1` for `/` is required. A dot in the key needs no escaping. Both confirmed:

```
PATH: /metadata/labels/signalloom.ai~1state
  after reconcile: state='stunned'  -> WORKS
  kustomization:   Ready=True ReconciliationSucceeded

PATH: /metadata/labels/signalloom.ai/state
  after reconcile: state='idle'  -> SILENTLY DID NOTHING
  kustomization:   Ready=True ReconciliationSucceeded
```

**The unescaped form does not error.** The CRD applies no pattern validation to `paths` (schema type is
plain `string`), the Kustomization stays `Ready=True`, and the rule quietly does nothing. This is the
easiest way to "fix" this bug and believe it worked. Any change here needs a test that asserts the label
survives a reconcile — not just that the Kustomization is Ready.

## 8. What this changes in `stun-under-flux.md`

- **Q1 is answered.** Yes, `reconcile: disabled` and `ssa: ignore` are honoured on individual objects by
  kustomize-controller v1.9.4 — but both un-manage the whole object, so neither is the right answer. The
  right answer is `.spec.ignore`, which §5 of that document does not mention because it lists
  SSA field ownership as "best fit, if honoured" without naming the field that implements it.
- **§5's table needs a new top row**: `.spec.ignore` — scope "one *field* of one object", suitable **yes,
  measured**. And a footnote that none of the rows below it apply on the ResourceSet path.
- **§7.2's "one-line fix" is wrong in its second half.** It offers "either drop the label from the
  manifest and let the runtime own it, or mark that field ignored". The first option is measured here to
  make things *worse* — the label is deleted outright rather than reverted. Only the second option works,
  and only if the literal stays.
- **§7.2's split-brain finding is stronger than stated.** The dashboard does not just show a stale
  `idle`; on the `op: remove` variant it shows *no state at all*, and `stunned_at`/`stun_reason` are wiped
  on every reconcile regardless. The evidence channel fails in two distinguishable ways, neither of which
  any current test catches.
