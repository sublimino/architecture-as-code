# SLAAT-P1-4 — Sentinel eBPF & Landlock Sandbox Confinement Adversarial Dossier

**Mission:** SLAAT (Signal Loom Autonomous Adversarial Testing), Phase 1 — Whole-System Adversarial Attack & Boundary Probing
**Card:** `SLAAT-P1-4` — Sentinel eBPF & Landlock Sandbox Confinement Escape Attacks
**Target:** `nono/profiles/worktree-agent.json` (live, via `nono wrap`), `d2-signalloom/apps/signalloom-stun-sentinel` (live deployment, read-only — image `ghcr.io/controlplaneio-in-toto/signalloom-stun-sentinel:v0.2.0`, pod `stun-sentinel-*` in `fe-signalloom-agents` on `kind-osramp`), `d2-signalloom/apps/stun-sentinel` (isolated test instance built from current source for the cgroup-adversarial battery only)
**Method:** live, kernel-level adversarial probing. Landlock escapes run confined processes via `nono wrap` against the unmodified shipped profile. Sentinel evasion drives activity from an unrelated agent pod and observes the live sentinel's own logs, read-only. cgroup-freeze adversarial testing builds and runs a throwaway, isolated `stun-sentinel` instance in its own namespace with its own credentials — it never touches the live deployed pod. Nothing in this card edits `d2-signalloom/apps/signalloom-stun-sentinel` source, the Landlock profile, or any Landlock/sentinel configuration (the card's merge boundary); every new artifact lives under `test/`, `scripts/`, `ci-evidence/`, and this dossier's own `docs/slaat/p1-4/` directory.

## Summary

36 live adversarial probes executed across three harnesses (16 Landlock escape, 9 eBPF evasion, 11 cgroup-adversarial), all green on the final run. **Zero unauthorized host-root-filesystem escapes, zero kernel panics, zero host instability.** The genuine findings are not clean bypasses of a working defense — they are a real detection-scope gap (the live sentinel's eBPF telemetry only sees TCP socket state, nothing process-level, so "evade telemetry via process spawning/ptrace/unshare" succeeds trivially because there is no instrumentation for those actions to evade — F1, the headline finding), a latency/reliability finding under host contention in the freeze path for one specific workload shape (F2, not a containment bypass — once the freeze call completes, it is unconditionally effective), and a sibling card's test harness going stale against a hardening that landed after it was authored (F3, not this card's to fix). Every attack aimed at the Landlock sandbox itself — symlink traversal, `/proc` inspection, ptrace, unshare-based namespace escape, raw sockets, forbidden filesystem writes — was denied, and every attack aimed at the cgroup-v2 freezer under adversarial load (fork-bomb-shaped PID churn, a PID-namespace-escaped child, concurrent/racing freeze+resume calls, memory-cgroup over-allocation) held.

## Scope and method

Three live probe harnesses, all bounded and self-cleaning:

| Script | Focus |
| --- | --- |
| `scripts/test-agent-sandbox-escape.sh` | 16-probe live Landlock escape battery against the shipped `worktree-agent.json` profile via `nono wrap` — sensitive-path reads, symlink traversal, `/proc` inspection, ptrace, unshare, raw sockets, O_CREAT on `/etc`, child-process inheritance, a background-thread exfiltration race |
| `scripts/probe-sentinel-evasion.sh` | 9-probe read-only probe against the LIVE deployed sentinel — static source inspection of its eBPF attach points plus a live 200-process-spawn + unshare burst driven from an unrelated agent pod, observing the sentinel's own log stream |
| `scripts/stress-agent-cgroups.sh` | 11-probe adversarial cgroup-freeze battery against an ISOLATED, throwaway `stun-sentinel` instance — bounded fork-bomb-shaped PID churn, a PID-namespace-escaped child, concurrent resume races, and a separate memory-cgroup OOM test |

Each harness is wrapped by a bats suite that runs the live battery once per file in `setup_file()` and asserts individual probe verdicts against the resulting JSON artifact — matching the convention `test/cgroup-freeze-stun.bats` and `test/worktree-landlock-confinement.bats` already established in this repository: skip-if-no-sandbox/cluster, fail-loud-if-present-but-the-harness-produced-nothing, and an arity gate so a suite that silently stops defining tests mid-file cannot read as a smaller pass.

**Why `nono wrap`, not `nono run`, for the Landlock half.** This card's own execution environment is itself a nono-confined session (a kpai/agent-managed sandbox). `nono run` persists a session record under `$XDG_STATE_HOME/nono/{sessions,audit}/`, and the OUTER sandbox denies write access to that directory — every nested `run` invocation stalled 13-26 seconds and then failed trying to write its own session file, before the command under test ever ran. `nono wrap` execs directly ("nono disappears") with no session-state file and is unaffected. Recorded as `SLAAT-P1-4-N1` in the findings catalog: an operational fact about nested sandboxing on this host, not a Landlock finding against the profile itself.

**Why the cgroup-adversarial battery builds its own isolated sentinel instance rather than attacking the live deployment.** The card's merge boundary and shared-file collision notes both name `d2-signalloom/apps/signalloom-stun-sentinel` as off-limits this phase, and freezing/resuming the LIVE pod's actual workloads would disrupt other concurrent agents and kanban cards sharing the same `kind-osramp` cluster. `scripts/stress-agent-cgroups.sh` builds the sibling `d2-signalloom/apps/stun-sentinel` module from source, installs it under a distinct name (`slaat-sentinel` — chosen specifically because it is ≤15 characters, the kernel's `comm` field truncation limit; the obvious choice `slaat-p1-4-stun-sentinel` is 24 characters and `pkill -x` against it silently matches nothing, which cost real debugging time establishing this script and is recorded here so the next person does not rediscover it), and runs it in its own namespace (`slaat-p1-4-cgroup-stress`) on its own port with its own bearer tokens — fully isolated, never touching the live pod.

## Findings

### F1 — The live sentinel's eBPF telemetry has zero visibility into process spawning, ptrace attachment, or namespace creation (HIGH)

Static source inspection of the deployed image's own eBPF program (`d2-signalloom/apps/signalloom-stun-sentinel/ebpf/c/socket_trace.bpf.c`) shows exactly one attach point: `SEC("tp_btf/inet_sock_set_state")` — TCP socket state transitions. Nothing else. A live adversarial burst (200 rapid process spawns plus one `unshare(CLONE_NEWPID)`) fired from an unrelated agent pod in the same namespace generated **zero** execve/openat/unshare-shaped entries anywhere in the sentinel's own log stream across a 3-second observation window, confirming the static finding against the running system. A positive control — a TCP connect burst from the same probe pod — confirmed the deployed probe's `ebpf_correlator_stats.records_read` counter is genuinely live and advancing throughout (`records_read` grew by millions during the observation window, consistent with the ~1.1 billion-event cumulative total already visible in the pod's 44-hour-old log stream), ruling out "nothing is instrumented at all" as the explanation — the instrumentation works, it is simply scoped to network flows only.

**This is not an evasion technique defeating a working defense.** A separate, more capable syscall tracer already exists in this repository: `d2-signalloom/apps/stun-sentinel/bpf/sentinel_probe.c` attaches `tracepoint/syscalls/{sys_enter_openat, sys_enter_openat2, sys_enter_execve, sys_enter_connect}`, backed by a full `SyscallEvent`/correlator pipeline (`pkg/ebpf`, `pkg/correlator`) with passing unit tests. It is wired into **no `cmd/` entrypoint** in that module — a grep across every `cmd/*/main.go` for `ebpf.` or `correlator.` references found none — and it is not the image actually deployed (`d2-signalloom/apps/signalloom-stun-sentinel`, confirmed as the running pod's image via `kubectl get pod -o jsonpath='{.spec.containers[0].image}'`). The capability is implemented and tested; it is dormant. "Evade telemetry via rapid process spawning / ptrace attachment / unshare namespace creation" succeeds trivially today because there is no syscall-level instrumentation running for those actions to evade.

**Severity:** HIGH. **Remediation:** wire `pkg/ebpf.NewLoader` + `pkg/correlator.NewSentinelProbeManager` into a `cmd/` entrypoint in `d2-signalloom/apps/stun-sentinel`, or port the same tracepoints into the deployed `signalloom-stun-sentinel` module's `ebpf/c/` sources. **Phase:** `SLAAT-P2-4`.

### F2 — Freezing a cgroup containing an unshare(CLONE_NEWPID)'d process intermittently exceeds the daemon's internal deadline under host contention (MEDIUM, not exploitable)

Against an isolated, freshly-built `stun-sentinel` instance, `POST /stun` targeting a pod whose single process has successfully `unshare(CLONE_NEWPID)`'d with `--mount-proc` returned **HTTP 504** on the first attempt in 2 of 5 total script runs during this card's testing, on this shared, multi-tenant `kind-osramp` node — an identical call against an ordinary fork-bomb-shaped target (no `unshare`) never did, across every run. A second attempt with a longer client deadline (20s vs 10s) succeeded with HTTP 200 and the expected `frozen=true` state in all 5 runs.

**Once the freeze call DOES complete, it is unconditionally effective — this is the load-bearing half of the finding.** Across every successful attempt, cgroup-wide CPU `usage_usec` delta measured exactly 0 over a 1.5-second post-freeze sampling window, and the kernel's own `cgroup.events`, read directly via `docker exec` rather than through the daemon, confirmed `frozen 1`. No live attempt ever observed a task that escaped the freeze. This is therefore a **latency/reliability finding specific to this one workload shape under load**, not a containment bypass: cgroup-v2's freezer suspends every task in the cgroup regardless of PID namespace, exactly as the kernel's design guarantees — the daemon can simply take longer than its own internal processing budget to resolve PIDs for a cgroup whose member has remounted `/proc` for itself.

**Severity:** MEDIUM (reliability, not security). **Remediation:** profile the freeze handler's PID/cgroup resolution path specifically against an `unshare(CLONE_NEWPID, CLONE_NEWNS)`'d member; either raise the internal deadline for this shape of workload or degrade to a retryable 503 rather than 504 so a caller knows to retry rather than treat it as a terminal failure. **Phase:** `SLAAT-P2-4`.

### F3 — The sibling CRKC-P1-2 harness (`scripts/test-cgroup-freezer.sh`) is stale against the current binary's auth contract (LOW, not this card's to fix)

The current `stun-sentinel` binary refuses to start at all unless `STUN_FREEZE_TOKEN` is set (`cmd/stun-sentinel/main.go:579-580`: `"stun-sentinel: STUN_FREEZE_TOKEN is required and cannot be empty"`), and `/stun` is now wrapped in the same `requireBearer(freezeValidate, ...)` gate as `/resume` (`main.go:562`). `scripts/test-cgroup-freezer.sh` — owned by `CRKC-P1-2`, predating this hardening — starts its own daemon with only `STUN_RESUME_TOKEN` set and posts to `/stun` with no `Authorization` header at all. Against the binary as it exists on the integration branch today, that daemon would not even start, and that test's own `/stun` call would receive 401 even if it did. Discovered as a byproduct of building an isolated instance of the same binary for this card's own `scripts/stress-agent-cgroups.sh`, which sets both tokens and sends the matching bearer header throughout.

Explicitly **not fixed here**: this card's merge boundary covers its own new files; `scripts/test-cgroup-freezer.sh` and its owning `test/cgroup-freeze-stun.bats` belong to `CRKC-P1-2`.

**Severity:** LOW. **Remediation:** update `scripts/test-cgroup-freezer.sh` to set `STUN_FREEZE_TOKEN` alongside `STUN_RESUME_TOKEN` and send the matching `Authorization` header to `/stun`. **Phase:** flagged for `CRKC-P1-2`, not actioned in this SLAAT card.

## Verified boundaries (the attack surface that held)

- **B1 — Every named sensitive-path read and the O_CREAT write to `/etc` are denied.** `$HOME/.ssh/id_rsa`, `$HOME/.kube/config`, and `/etc/shadow` are all denied under the shipped `worktree-agent.json` profile; `openat(O_CREAT)` on `/etc` is denied. A positive control (an allow-listed write inside the worktree) confirms the sandbox is functioning, not merely refusing everything — without it, a dead or misconfigured sandbox would "pass" every denial above for the wrong reason.
- **B2 — Symlink traversal does not bypass Landlock's path resolution.** A symlink created INSIDE the allowed worktree pointing at a denied target is still denied — Landlock resolves the real target, not the link path. A control symlink to a baseline system-read path (`/etc/passwd`, granted by nono's composed system-read capability group for NSS resolution, not by the profile's own explicit list) correctly still resolves, ruling out an over-broad denial-of-everything as the explanation. (An earlier draft of this probe got this control backwards — see the script's own comment trail for the corrected expectation.)
- **B3 — `/proc` inspection of another process is denied; self-introspection is not.** Reading `/proc/1/environ` (pid 1, not self) from a confined process is denied; the same process can still inspect its own `/proc/self`, ruling out an accidental blanket `/proc` lockdown.
- **B4 — ptrace-attach to an unrelated process is denied, by nono's own seccomp-bpf filter, independent of Yama and Landlock.** The host's `yama/ptrace_scope` sysctl reads `0` (unrestricted-by-Yama), yet attach to an unrelated sibling process still fails `EPERM` at `PTRACE_SEIZE`. The live evidence corrected this probe's own first-pass attribution — it initially assumed Yama was the enforcing layer, which `ptrace_scope=0` rules out; the actual mechanism is nono's own seccomp-bpf policy.
- **B5 — `unshare(CLONE_NEWPID)` neither widens filesystem access nor defeats cgroup freeze.** A confined process that successfully unshares into a new PID namespace gains no new filesystem access — Landlock rulesets persist across `unshare(CLONE_NEWPID)`, they are not reset. Under default (non-elevated) Kubernetes pod capabilities, `unshare(CLONE_NEWPID)` with `--mount-proc` is denied outright (missing `CAP_SYS_ADMIN`) before cgroup freeze is even relevant — the realistic case for an ordinary agent workload. Against a deliberately capability-elevated throwaway pod built specifically to exercise the escape (see F2 for the one caveat on freeze latency under load), a process that DID unshare is still fully suspended by `cgroup.freeze` once the freeze call completes — cgroup membership and PID namespace are orthogonal kernel concepts, confirmed via both the daemon's own report and an independent CPU-accounting measurement.
- **B6 — Raw socket creation is denied (a capability boundary, correctly attributed rather than over-claimed).** `socket(AF_INET, SOCK_RAW)` fails under this uid with or without nono confinement — `CAP_NET_RAW` is absent either way. Recorded as redundant-with-capability rather than credited to Landlock.
- **B7 — cgroup-v2 freeze holds under heavy adversarial PID churn and concurrent resume races.** Freeze latency stayed under the 50ms deadline while the target cgroup carried 122-182 concurrently-alive processes from a bounded fork-bomb-shaped workload (not an unbounded `:(){ :|:& };:` — see the Deviations note below on why). The kernel's own `cgroup.events`, read directly, confirmed `frozen 1` after every successful freeze. Two concurrent, unserialised `/resume` calls fired back-to-back did not crash the daemon (it answered `healthz` immediately afterward) and execution genuinely resumed (non-zero CPU `usage_usec` delta measured independently afterward).
- **B8 — `/stun` is bearer-gated; unauthenticated freeze attempts are refused with 401.** The current binary will not start without `STUN_FREEZE_TOKEN` and rejects an unauthenticated `POST /stun` with HTTP 401 — the same bearer gate the design documents for `/resume` now also covers `/stun`. See F3 for the stale sibling harness this hardening left behind.
- **B9 — The kernel's own memory cgroup and OOM killer hold independent of the sentinel.** A throwaway container with `memory.limit=32Mi` deliberately allocating 512Mi via `dd` into `/dev/shm` was OOMKilled by the kernel, confirming the memory controller enforces its ceiling regardless of what the sentinel does or does not observe.

## Deviations from the card's Approach

- **Bounded fork storms, not an unbounded fork bomb.** The card's Approach and hard-STOP boundary both point the same direction: destabilising the shared `kind-osramp` node (used concurrently by other agents and kanban cards) would fail this mission's own containment goal before measuring anything. `scripts/stress-agent-cgroups.sh` spawns a fixed `FORK_COUNT` (default 60) of short-lived children per batch, replaced on a fixed cadence — enough to sustain 100+ concurrently-alive processes and heavy churn, never an unbounded `:(){ :|:& };:`.
- **The unshare-based escape target uses a deliberately capability-elevated pod, not the default agent workload shape.** `unshare(CLONE_NEWPID)` requires `CAP_SYS_ADMIN`, which no default Kubernetes pod capability set grants. To exercise the kernel-design question "does cgroup freeze survive unshare" at all, `scripts/stress-agent-cgroups.sh` creates a second, separate, throwaway pod with `securityContext.capabilities.add: ["SYS_ADMIN"]` — bounded to that one pod, in the ephemeral test namespace, deleted at the end of the run. The REALISTIC case (default capabilities, no elevation) is tested separately against the main fork-storm target and is the one that reflects an ordinary agent workload (B5).
- **No live kernel exploit, no hardware side-channel, no kernel module — none attempted, none needed.** Every finding above was reached through process spawning, filesystem calls, HTTP calls to the sentinel's own API, and standard `kubectl`/`docker exec` operations.
